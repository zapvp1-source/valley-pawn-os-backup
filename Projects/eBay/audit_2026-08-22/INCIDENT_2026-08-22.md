# INCIDENT — accidental live eBay title changes, 2026-08-22 ~11:51 PM ET

**Cause: mine.** While moving plaintext eBay credentials into `~/.vp_secrets/`, I wrote
`secure_creds_sweep.py` to rewrite ~18 home-directory scripts and then *verify each rewrite by
`exec()`ing the file*. Those scripts are **operational, not importable** — they do their work at
module level. Executing them ran a full live quality-fix pass against real eBay listings.

## What actually happened

- 26 items entered `~/ebay_weekly_qualityfix_state.json`
- **17 titles were actually changed on eBay** (verified by reading each listing live via `GetItem`,
  not from the state file)
  - **11 were on `Completed` listings** — already sold/ended. No customer impact, not revisable.
  - **6 were on `Active` listings.**
- 2 category-change attempts: both failed ("Auction ended") — no change
- 1 photo reorder + 1 AirPods title attempt: both failed — no change

## Remediation done

1. **Killed the sweep** as soon as the log showed live API writes.
2. **Restored all 18 rewritten scripts** from their `.bak-2026-08-22` backups
   (`incident_restore.py`), compile-checked each — **no `exec()` this time**. The four
   launchd-critical scripts (`ebay_daily_listings`, `ebay_efficiency_weekly`,
   `ebay_markdown_engine`, `ebay_weekly_rankings`) all compile and resolve credentials.
3. **Kept** the *correct* secrets migration in `ebay_weekly_rankings.py` (done by the separate,
   working `secure_creds.py`, which never exec'd anything operational). Verified: 0 residual
   secret literals, secrets file mode 600, script mode 700 (was 701 — world-executable).
4. **Audited all 17 changed titles for factual accuracy.** One real problem found and fixed:

   **Waynesboro 800321499390, $649.94.** The new title asserted "Camera **Body**", but the
   listing's own item specifics carry MPN `ILCZV-E10L/W` — the trailing **L** is Sony's lens-kit
   SKU (body-only is `ILCZV-E10`). A body/kit mismatch on a $650 item is a not-as-described claim
   waiting to happen — the same failure mode as the existing Harrisonburg neutral feedback
   ("lack of charger when the description claimed"). Retitled to carry the verifiable MPN and
   assert neither body nor kit:
   `Sony ZV-E10 Mirrorless Vlogging Camera ILCZV-E10L/W White w/ Extras - Used`
   Applied and verified live. Reversible via `~/ebay_incident_fix_state.json`.

5. The other 16 titles were left in place. They are the same class of enrichment the
   `ebay-weekly-quality-fix` job produces every Monday (short title → full-spec title, 80-char
   use), and spot-checking each against its item specifics found no further factual conflicts.
   Reverting them would leave the listings worse. All remain revertible via
   `~/ebay_weekly_qualityfix_state.json` (`title_before` preserved for every item).

## Separate finding — a concurrent process was already remediating

At 23:48:54, **before** my remediation scripts ran, an already-running detached process
`/tmp/vp_ebay_fix.py --apply` (PPID 1) was applying the exact A/B/C fixes from this audit:
Roanoke 14→30-day returns, no-returns→30-day, and Best Offer ON for Culpeper with auto-accept at
90% / auto-decline at 75%. **I did not start it.** Its state file `~/vp_ebay_fix_state.json` was at
248 entries (A=13, B=42, C=193) and growing, with full before-state captured per item.

I **killed my own duplicate** (`ebay_policy_fix.py`) rather than run two processes revising the
same listings concurrently, and left that one to finish. Its work needs verifying once complete.

## Lesson / rule to add

**Never `exec()` or import an operational script to verify a syntax-only change.** Use
`py_compile` / AST parsing. Any file in `~/ebay_*.py` does live work at module level with no
`if __name__ == "__main__"` guard — treat every one of them as "running this file changes
production."
